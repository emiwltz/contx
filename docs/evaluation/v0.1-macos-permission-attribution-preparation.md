## Purpose and authorization boundary

The identity-only probe proved that LaunchServices recognizes a native
`io.contx.identity-probe` application instead of an unbundled Python process.
An explicitly authorized read-only Keychain inventory then reported zero code-
signing identities and zero valid code-signing identities. No Apple Development,
Developer ID, expired, or otherwise matching code-signing identity was available
with a corresponding private key.

Emi authorized preparation of a one-off permission-attribution test without
triggering a permission or collecting activity. This preparation was allowed to:

- add gated native request and verification paths that are not executed;
- include a minimal Python child that only preflights existing Screen Recording
  access;
- compile and ad-hoc sign a disposable complete bundle;
- launch only the identity path, which calls no privacy API and no child;
- inspect content-free process identity and aggregate CONTX counters;
- delete every generated bundle and evidence file after the dry-run.

It did not authorize a Screen Recording request, a permission preflight, child
execution, title or pixel access, collector integration, LaunchAgent, background
activation, or real-data pilot. Emi later authorized the request, the temporary
move and LaunchServices registration, and the preflight-only verification as
three separate action-time gates. None of those later authorizations included
capture, collection, background activation, or collector integration.

## Three isolated modes

The prepared native executable has three explicit modes:

| Mode | Allowed behavior | Gate |
|---|---|---|
| `identity` | Report only the bundle's own identity and exit at a 1–30 second bound | Rejects confirmation and child arguments |
| `request` | Preflight existing access once, then call `CGRequestScreenCaptureAccess` once and report the Boolean results | Exact phrase `REQUEST CONTX IDENTITY PROBE SCREEN RECORDING`; rejects a child path |
| `verify` | Preflight from the native app, then launch the sealed child script with the exact configured Python and report both results | Exact phrase `VERIFY CONTX IDENTITY PROBE SCREEN RECORDING`; requires a new, private child-evidence path distinct from the native evidence path |

The executable hard-codes `pixelsRead: false` and `collectionStarted: false` in
every native result. It contains no ScreenCaptureKit, screenshot manager, display
capture, window-list capture, Accessibility, workspace-observation, or CONTX
collection call.

The request and verification phrases are separate so a request authorization
cannot be replayed as verification. Neither phrase was used during preparation;
each was later used exactly once under its own explicit authorization.

## Manifest and user-facing explanation

Apple documents that an application using ScreenCaptureKit must include
`NSScreenCaptureUsageDescription` with a clear explanation before requesting
Screen Recording access. The permission-probe builder therefore requires a
40–240 character, single-line description and refuses to invent a default.

The compile-only preparation and later authorized request used this text:

> CONTX vérifie uniquement l’attribution de la permission, sans capturer ni
> enregistrer l’écran.

Emi approved the wording before the request. macOS then displayed its system
dialog and offered to open the Screen Recording settings.

## Python child boundary

The child source is stored as `Contents/Resources/permission_child.py` with mode
`0600` before the bundle is signed, so the code signature seals that exact
resource. It imports only standard-library modules and `Quartz`, calls
`CGPreflightScreenCaptureAccess` exactly once, and writes only:

```json
{
  "collection_started": false,
  "permissions_requested": false,
  "pixels_read": false,
  "probe_kind": "python_child_preflight",
  "schema_version": 1,
  "screen_recording_available": false
}
```

The final value can be either `true` or `false`; `false` above illustrates the
JSON Boolean type without implying the expected permission state.

The builder requires one absolute executable Python path. It embeds that path as
base64 rather than exposing a mutable runtime argument, calculates the
interpreter's SHA-256 digest, and seals both values into the native executable.
Before launching the child, the native app confirms that the configured path is
still executable and that its bytes still match the build-time digest. The child
receives a minimal environment, no arbitrary command, and a five-second bound;
the parent terminates it and reports status 124 after a timeout.

The external PyObjC installation used by that interpreter is not embedded or
sealed by the app bundle. For the one-off supervised experiment, the exact
virtual environment must remain unchanged from bundle construction through
verification, and the bundle plus TCC grant must be removed afterward. This is
an explicit experiment limitation, not an accepted production boundary.

## Builder safety and regression coverage

The original identity builder now delegates its staging to a shared
`ProbeBundleSpec` path. Both bundle kinds still:

- require macOS and a new absolute `.app` destination;
- require an existing parent directory with no group or other access;
- reject duplicate or unsafe resource names and Info.plist keys;
- compile into a private sibling staging directory;
- write resources and the binary before signing;
- ad-hoc sign with the exact experimental identifier;
- perform strict deep signature verification;
- atomically publish only a complete bundle;
- remove staging state after success or failure;
- never launch an application from the builder.

Targeted tests cover the existing identity behavior, private bundle/resource
modes, the sealed child, embedded Python path and digest, mandatory usage text,
three native modes, distinct confirmation phrases, capture-API exclusions,
preflight-only child source, invalid Python paths, compilation failure cleanup,
and strict typing.
