# v0.0.1 validation record

**Date:** 2026-08-02

**Scope:** J0 engineering foundation and the minimal project-resumption
vertical slice

## Outcome

The v0.0.1 exit gate is satisfied on the target development Mac.

The positive flow is:

```text
five synthetic app observations
    -> project-resumption and brief-activity events
    -> one accepted and one rejected memory candidate
    -> one OptMem entry with SQLite provenance
    -> direct contx wake output
```

The accepted candidate is marked `stored`. Its `MemoryLink` references the
candidate, source event, and all source observations. Replaying the fixture
creates a new `ProcessingRun` but no duplicate observation, event, candidate,
link, or OptMem record.

## Verification

The following checks passed from the repository environment:

```text
uv run ruff check .                  pass
uv run ruff format --check .         pass
uv run mypy                          pass, strict package check
uv run pytest -q                     45 passed
uv build --no-sources                sdist and wheel built
```

The built wheel and source distribution contain the CONTX package, migration,
synthetic fixture, `py.typed`, and project license. They do not contain the
ignored OptMem clone or runtime data.

The wheel was installed with its 18 runtime dependencies into a fresh Python
3.12.13 virtual environment. From outside the source checkout, the installed
`contx` entry point completed the synthetic run and `wake` flow using the
explicit reviewed OptMem executable, and reported version `0.0.1`.

The real reviewed OptMem snapshot was exercised in an isolated temporary
runtime. Two identical `run-once` executions produced database counts of five
observations, two events, two candidates, one memory link, and two processing
runs. The fixed-width OptMem log contained one 320-byte record. `contx wake`
returned:

```text
#0 2026-08-02 Resume CONTX from its current implementation state; sustained project work resumed after a multi-day gap.
You are awake.
```

All OptMem and CONTX state files in that runtime were mode `0600`; owned
directories were mode `0700`.

## Failure and privacy evidence

- An injected failure after memory append but before SQLite linkage recovered
  on replay without creating a second memory.
- Adapter tests cover an unavailable or modified executable, timeout, bounded
  output, invalid UTF-8, over-limit entries, and pending maintenance.
- Subprocess environment tests confirm unrelated environment secrets are not
  forwarded to OptMem.
- Pipeline failures persist a bounded error code and no private exception
  message.
- Synthetic and live observations contain no window title, screenshot path,
  or OCR artifact.
- The active-app command leaves no CONTX background process.
- No network service or model provider exists in this increment.

## Host-dependent live smoke result

The AppKit dependency imported successfully. In the automation host session,
macOS returned no frontmost application. CONTX reported the precise,
non-private capability error:

```text
Error: macOS did not report a frontmost application
```

The failed run was recorded as `collector_unavailable`, with no private error
summary and no observation. This is an accepted v0.0.1 outcome because the
live collector must either work in the current graphical session or report a
precise capability limitation.

## Residual limitations carried forward

- OptMem maintenance can be detected and transported, but automatic offline
  compression is a v0.5 requirement.
- Exact-text recovery is intentionally narrow. Cross-candidate semantic
  deduplication and supersession belong to the complete memory lifecycle.
- The ignored OptMem development snapshot cannot be bundled publicly until
  redistributable permission is documented.
- Continuous collection, pause/resume, exclusions, raw retention/purge, and
  selective screenshots begin in v0.1; none is silently enabled here.
- The macOS collector still needs an interactive-session smoke test where a
  frontmost application is available.
