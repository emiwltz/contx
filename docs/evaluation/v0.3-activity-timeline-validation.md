# v0.3 activity timeline validation

**Status:** Complete for the J3 exit gate

**Evidence date:** 2026-08-02

## Outcome

J3 now builds deterministic, intelligible activity timelines from successful
local-model transformations without collecting new data or invoking a second
semantic model pass. A frozen synthetic day proves sessionization, structured
events, version comparison, append-only correction, and exact provenance.

No real screenshot, title, background collector, or user activity was used or
activated for this validation.

## Implemented boundary

The event layer now provides:

- a closed `EventType` vocabulary with bounded normalization of model labels;
- deterministic sessions based on time, maximum duration, project,
  application, and compatible activity type;
- configurable 10-minute gap and two-hour maximum defaults;
- conservative aggregation of summaries, observed facts, inferred context,
  confidence, sensitivity, projects, entities, and memory relevance;
- explicit `valid_from` and `valid_until` fields beside the evidence period;
- a stable evidence `lineage_key` independent of processing version;
- one content-free `TimelineBuild` record for every window, version, and
  session policy;
- processing-run snapshots that select only their own events;
- append-only full semantic correction snapshots with a linear supersession
  chain;
- effective timeline entries that apply only the latest correction while
  retaining the original event and evidence;
- CLI commands to build, inspect, and correct explicit timeline snapshots.

The commands are:

```sh
contx timeline build \
  --from 2026-08-02T00:00:00+00:00 \
  --until 2026-08-03T00:00:00+00:00
contx timeline show <processing-run-id>
contx timeline correct <event-id> \
  --summary "Corrected event summary" \
  --reason "Why the interpretation was wrong"
```

`timeline build` reads only persisted, successful model transformations. It
does not collect, access raw images, or contact Ollama. `timeline show` prints
semantic event content only after an explicit user command. A correction is a
deliberate durable write and does not mutate source evidence.

## Frozen-day proof

The main integration fixture contains four synthetic successful
transformations:

1. CONTX coding from 09:00 to 09:10;
2. CONTX testing from 09:15 to 09:25;
3. another project's research from 11:00 to 11:20;
4. CONTX activity on the following day, outside the selected window.

With `session-events-v1`, the selected day produces:

```text
in-window transformations: 3
timeline events: 2
event 1: project_work, project CONTX, 2 observations, 2 transformations
event 2: research, project OTHER, 1 observation, 1 transformation
outside-window transformations included: 0
```

The first event combines the two compatible CONTX segments into the readable
summary:

```text
Editing the CONTX timeline. Running CONTX timeline tests.
```

Every event retains ordered source observation identifiers plus foreign-key
links to each successful model transformation and the timeline processing run.

## Replay and correction proof

Rebuilding the same day with `session-events-v1` produced the same two event
identifiers. The second processing run linked those existing events, and the
event table remained at two rows.

Rebuilding the same day with `session-events-v2` produced two distinct event
identifiers with the same two evidence lineage keys. Both v1 and v2 snapshots
remained readable, and the event table contained four rows rather than erasing
the first version.

The fixture then appended a correction to the v1 CONTX event, changing its
summary, confidence, and epistemic status to `hypothetical`. Reading the v2
snapshot applied that same correction because the source-observation lineage
was unchanged. The v2 event identifier remained distinct, its sensitivity and
evidence remained model-derived, and the original v1 event stayed unchanged.
Retrying the same correction identity returned the existing record rather than
creating a duplicate.

Repository tests additionally prove that:

- a correction cannot target a missing event or mismatched lineage;
- a new correction must supersede exactly the current lineage head;
- two terminal heads are treated as a corrupted fork;
- the migration backfills lineage and validity for existing events;
- the migration schema exactly matches SQLAlchemy metadata;
- unknown legacy event labels remain readable as bounded `other` events.

## Failure and privacy behavior

- Naive CLI time boundaries are rejected before a timeline run is created.
- Invalid windows, thresholds, correction content, and correction chains fail
  at typed boundaries.
- The builder never changes or lowers event sensitivity.
- A successful transformation scan is capped at 10,000 items; exceeding it
  fails visibly rather than emitting a partial snapshot.
- Corrections are durable user-authored semantic content. They still pass
  through the later J4 candidate and durable-memory gates; J3 does not write
  them to `MemoryStore`.
- Raw screenshots may expire after interpretation because sessionized events
  depend on persisted validated transformations and observation metadata.

## J3 completion and residual risk

The J3 exit gate is satisfied: a frozen day produces a deterministic readable
timeline, every event cites observations and model transformations, corrections
survive compatible rebuilds, a same-version replay is idempotent, and changed
versions remain comparable without deleting prior evidence.

The 10-minute and two-hour thresholds are initial defaults, not empirically
final daily-use values. Real-world calibration, long-duration query cost, and
incremental scheduling remain pilot work. Real collection is still separately
gated by J1 and was not implied by completing this synthetic J3 proof.
