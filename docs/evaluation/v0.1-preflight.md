# v0.1 macOS collection preflight

**Status:** In progress; not a v0.1 completion claim

**Evidence through:** 2026-08-22

## Purpose

This report separates implementation evidence from live-product evidence for
J1. Synthetic tests prove privacy ordering, persistence, recovery, and native
boundary contracts. The explicitly authorized native smoke below also proves
the target-Mac permission UX and synthetic focused-window path. Neither can
prove a controlled day, target-Mac resource baselines, or launchd supervision
in the real user session.

## Proven without persistent activation

The current implementation and automated fixtures prove that:

- background collection is disabled in the default private configuration;
- a disabled configuration refuses to build the daemon before creating its
  database;
- one activity sample is shared across duration, title, and screenshot paths;
- pause is read before application metadata or pixels;
- application exclusions are evaluated before an optional title read;
- title exclusions prevent screenshot and sensitive metadata persistence;
- an enabled production daemon composes the permission-gated native
  ScreenCaptureKit screenshot source instead of requiring a test-only injected
  source;
- the native source selects one frontmost layer-0 window by process, bundle,
  and window ID, excludes its shadow and every other window or display, and
  refuses missing or changed context without a broad fallback;
- the PyObjC bridge receives explicit public block metadata for the
  `SCShareableContent` and `SCScreenshotManager` completion handlers before
  either selector is resolved, including the exact `CGImageRef` result type;
- the exact window ID is bound into the initial ephemeral sample, so another
  window of the same process cannot be silently selected after policy
  authorization, even when title collection is disabled;
- focus races and applications without a capturable window skip only that
  screenshot, apply the minimum-interval retry bound, and do not stop metadata
  collection;
- process and window IDs remain ephemeral collection metadata and are absent
  from stored observations and public contracts;
- a host-dependent smoke harness now creates two synthetic AppKit windows,
  requires the exact confirmation phrase `CAPTURE CONTX SYNTHETIC WINDOW`,
  proves that switching to the second window rejects the first window's sample,
  and writes the successful PNG exclusively with mode `0600` for explicit
  visual review;
- the smoke harness never requests permission, changes configuration, starts a
  background process, or silently overwrites an artifact;
- Accessibility and Screen Recording preflights never request permission;
- the separate permission setup command requires an exact selected flag,
  explains why access is needed, issues one native request, collects no
  activity, and reports the relevant System Settings path without retrying;
- inactive, locked, and asleep samples contain no application metadata;
- segments are bounded and flushed on pause, shutdown, or failure;
- the raw store is private, budgeted, and limited to 48-hour retention;
- startup and scheduled purge remove expired observations and orphaned files;
- exact consecutive screenshot content is discarded while same-sample retries
  remain idempotent;
- one exclusive process lease makes daemon status truthful;
- AppKit menu creation errors, rejected accessory policy, and programmatically
  reported invisibility close the audited run; the 2026-08-22 supervised test
  proved that `NSStatusItem.isVisible` is not optical evidence on the target
  Mac, so an observed menu remains a separate activation gate;
- SIGINT and SIGTERM become orderly main-loop stop requests;
- the collector and periodic-processor LaunchAgent plists are deterministic,
  use an absolute executable, apply umask `077`, target the Aqua session,
  bound restart/invocation cadence, and write only to CONTX log paths;
- the package exposes dedicated regular `contx-collector` and
  `contx-processor` executables, and the wheel records both console entrypoints;
- read-only background status checks desired title/screenshot permissions,
  local model availability, the reviewed OptMem checksum, current schema,
  effective pause state, manifest ownership and loaded labels without changing
  configuration, collection control or managed manifests, and without starting
  a managed job or collection process;
- activation and deactivation require distinct exact confirmation phrases;
  activation persists a pause before staging only missing private manifests,
  atomically enables the three accepted v0 feature flags, bootstraps both user
  jobs together, resumes only after the complete active state is verified, and
  restores only its own changes after a partial failure or interruption;
- deactivation pauses first, refuses unmanaged loaded jobs, unloads both jobs,
  disables the three flags, and removes only exact stopped manifests after
  prevalidating the whole removal set;
- the internal daemon entrypoint sanitizes unexpected failures.
- the short-lived processor entrypoint sanitizes failures, treats a bounded
  backlog as expected deferral, and refuses the default disabled background
  state before creating a database;

## Authorized target-Mac title and screenshot evidence

On 2026-08-13, Emi explicitly authorized the narrow permission and synthetic
capture path. No persistent collection or user application was placed in
scope.

1. `contx permissions request --accessibility --screen-recording` explained
   each purpose and both native APIs reported `granted`.
2. The harness ran inside a real `NSApplication` event loop and required the
   exact confirmation phrase below.
3. Accessibility returned the exact title `CONTX Synthetic Focused Window`.
4. After the second window replaced the first within the same process, the
   title-independent source rejected the original sample with
   `focused_window_changed` before resolving shareable content or pixels.
5. After focus returned, ScreenCaptureKit captured the exact primary window as
   a 1280 x 856 RGBA PNG. Its SHA-256 was
   `41c7b62ad72ef9ac5f13f9031b09bd82434c16d7c40c65ae30f8c7b3dc368e8a`.
6. Local inspection confirmed the synthetic title, blue opaque content, and
   absence of the red race window or user content. The only artifact was owned
   by the local user with mode `0600`, then explicitly deleted with its empty
   temporary directory.
7. The harness requested no permission itself, changed no configuration, and
   started no background collection.

The live run exposed and fixed two integration defects that synthetic mocks did
not reveal: a CLI-created AppKit fixture must execute its workflow inside the
real `NSApplication` loop, and the PyObjC 12.2.1 bridge on macOS 26.5.2 lacks
the two completion-block signatures at runtime. CONTX now supplies those
signatures through PyObjC's public metadata registry before using either API.

The reproducible command remains:

```text
uv run python scripts/smoke_macos_focused_window.py \
  --output /private/tmp/<new-private-name>.png \
  --confirm "CAPTURE CONTX SYNTHETIC WINDOW"
```

On the same target Mac, `contx background status` subsequently reported the
configuration disabled, both manifests missing, both labels unloaded, and
`preflight: ready`. That content-free result proves that the current
permissions, loopback model, reviewed OptMem executable, schema and packaged
entrypoints satisfy activation prerequisites. It did not stage a plist, change
configuration, load a job, or start collection.

After the lifecycle pause/rollback contract was stabilized on 2026-08-22, an
initial sandboxed readiness invocation could not observe the host permission
state or local-model service. A subsequent host-scoped read-only check reported
both permissions available, the configured local model ready, both manifests
missing, both labels unloaded, and `preflight: ready`. This distinction is
important: sandboxed capability results were not treated as host evidence.

## Authorized supervised commissioning evidence

On 2026-08-22, Emi explicitly authorized the first supervised activation after
reviewing the privacy boundaries, 43 strict application exclusion rules, the
48-hour retention policy, and the temporary 1 GiB raw-disk limit.

1. Activation created the exact private collector and processor manifests,
   loaded both jobs, and resumed collection only after the complete background
   status reported active.
2. The collector remained running and the short-lived processor completed with
   exit code 0, but Emi could not see the expected `CONTX` menu-bar item.
3. Collection was immediately paused. Raw usage, backlog, and accepted records
   remained at zero; no user activity, title, or screenshot was persisted.
4. The first deactivation command received launchd bootout code 0 but checked
   the collector before its asynchronous shutdown completed and therefore
   reported a false failure. A few seconds later the service was absent. A
   second deactivation completed removal of both exact manifests and restored
   configuration-disabled, paused, inactive state.
5. `lsappinfo` identified the supervised collector only as unbundled `python3`,
   without a bundle identifier or application name. A menu-only LaunchAgent
   then called `finishLaunching`, reported accessory policy and
   `NSStatusItem.isVisible == true`, and still produced no user-visible item.
6. A second menu-only test launched through a temporary `LSUIElement` app.
   LaunchServices registered `CONTXMenuSmoke` with bundle identifier
   `io.contx.menu-smoke.app`. Emi initially missed its deliberately long
   `CONTX BUNDLE TEST` label, then observed `CONTX` briefly before the bounded
   test exited. The target menu contains many items, so available menu-bar width
   is now the leading explanation for the unreliable optical result. Both
   synthetic tests called no collector, database, activity, title, screenshot,
   or model component and removed their temporary jobs, bundles, and logs.
7. The target-Mac test additionally proved Apple's documented AppKit behavior:
   `NSApplication.stop` called from a timer does not exit until an actual event
   is dispatched. A private application-defined wake event made the second
   smoke exit automatically at its bound.
8. Emi then explicitly approved replacing the wide text with a compact square
   status item. The target Mac provided all three built-in symbols:
   `record.circle.fill` for active, `pause.circle.fill` for paused, and
   `circle.slash` for disabled. Emi observed the active circle first through a
   bounded `LSUIElement` app and then again from a raw temporary LaunchAgent,
   matching the real collector's supervision context. Both tests used an
   in-memory menu model only, produced no error, called no collection component,
   and removed their temporary process, job, bundle, plist, and logs.

Later on 2026-08-22, Emi explicitly authorized a second supervised activation
with the compact controller and the same reviewed privacy limits.

1. The host-scoped preflight reported `ready`: the configured Gemma model was
   installed with vision capability, the schema was current, the collection
   control was paused, both LaunchAgent manifests were absent, raw usage and all
   backlogs were zero, the 43 application exclusions were enabled, and the
   temporary raw-disk budget remained 1 GiB.
2. Activation created and loaded both private manifests, resumed collection,
   and reported both jobs active. Emi observed the compact active circle in the
   real collector, so the production menu-bar visibility gate passed.
3. The periodic processor completed normally with exit code 0. The collector,
   however, exited twice with `macOS screen-capture permission is required`.
   Collection was immediately paused; raw usage and every backlog remained zero.
4. A host-scoped interactive capability check then reported both window-title
   and screenshot permissions available. One bounded resume reproduced two more
   screen-capture permission failures in the LaunchAgent collector while still
   persisting zero bytes and zero backlog. Collection was paused again.
5. The interactive command and LaunchAgent use the same ad-hoc, unbundled Python
   interpreter, but macOS evaluates them under different launching contexts.
   The protected TCC database could not be read, so its internal attribution was
   not inspected. The observed difference is nevertheless consistent with a
   responsible-application identity gap: interactive CONTX inherits an
   authorized application context, while the raw launchd child has no dedicated
   CONTX application identity. Granting Screen Recording to the shared Python
   interpreter would be broader than CONTX and is explicitly rejected as an
   unsafe pilot workaround.
6. Deactivation unloaded both exact labels, removed both manifests, disabled
   title and screenshot collection, and restored an indefinitely paused state.
   The final host status was inactive with zero raw usage, zero accepted work,
   and zero backlog.

The resulting narrow lifecycle corrections now:

- finish AppKit launch before native menu and collection startup;
- validate the final accessory policy rather than the setter's ambiguous
  Boolean return;
- reject programmatically reported menu invisibility, while retaining the
  stronger human-observation activation gate;
- post one application-defined event after `stop` so timer-driven shutdown
  returns to the audited cleanup path;
- wait up to five seconds for an accepted launchd bootout to finish before
  reporting a stuck service, including activation rollback.

The compact menu design is accepted: direct user observation proved it visible
in both synthetic contexts and in the real collector. The current raw
Python/PyObjC LaunchAgent is **not accepted for persistent screenshot
collection**, because its screen-capture authorization differs from the
interactive preflight and causes a restart cycle. Before another real
activation, CONTX needs a dedicated macOS application identity whose permission
scope is limited to CONTX. The smallest reliable app-bundle design must be
evaluated first; ADRs 0007 and 0019 already define a small signed Swift helper as
the replacement boundary if Python packaging cannot meet that requirement. No
further real activation is authorized by this commissioning attempt.

## Explicitly not yet proven

The following J1 exit criteria remain open:

1. observing the accepted compact controller inside a newly authorized real
   collector activation; synthetic raw-LaunchAgent visibility and actual
   collector install/load/unload have been proven separately;
2. one controlled day of target-Mac collection;
3. measured CPU, memory, detection latency, and raw-disk baselines;
4. restart and recovery behavior under the installed supervisor;
5. review of the resulting real records for missed exclusions and usefulness.

These are action-time gates. The completed synthetic authorization does not
authorize CONTX to install persistence or collect real user activity.

## J1 exit decision

J1 remains **in progress** until every open item above has direct evidence.
Passing synthetic tests is necessary but insufficient. Work on later offline
pipeline stages may proceed with synthetic fixtures while these live gates
remain closed, but v0.1 and the complete v0 cannot be declared finished.
