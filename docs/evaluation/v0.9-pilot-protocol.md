# v0.9 real-pilot protocol

**Status:** Deterministic harness implemented; real-data execution not started

**Evidence date:** 2026-08-02

## Outcome so far

CONTX can now prepare, validate, score, and report a 7- to 14-day paired pilot
without enabling collection. The evaluator has strict versioned records,
private file permissions, cutoff-aware aggregation, explicit incomplete/fail/
review/pass gates, and a report that excludes ground-truth summaries and agent
answer content.

This is infrastructure evidence only. No permission was requested, no
LaunchAgent was installed, no real title or screenshot was read, and no pilot
day has elapsed.

## Action-time gates before day 1

The following actions remain separately prohibited until Emi approves them at
the moment they are about to occur:

1. requesting Accessibility permission;
2. requesting Screen Recording permission;
3. enabling live window-title or screenshot collection;
4. enabling persistent background collection;
5. installing or loading the user LaunchAgent;
6. beginning the real-data pilot.

Before that approval, review the exact exclusion list, retention, screenshot
cadence, pause behavior, deletion recovery path, and the CPU/RAM/detection
limits that make daily use acceptable. A prepared evidence directory is not a
pilot start and grants none of these permissions.

## Preparing the private workspace

After start/end dates and resource limits are accepted:

```sh
contx pilot prepare /absolute/private/pilot-directory \
  --start 2026-08-03T08:00:00+02:00 \
  --end 2026-08-10T08:00:00+02:00 \
  --max-p95-cpu <percent> \
  --max-p95-rss-bytes <bytes> \
  --max-p95-detection-ms <milliseconds>
```

The command requires a new or empty directory, protects it with mode `0700`,
creates files with mode `0600`, and prints that collection remains unchanged.
It includes `EXAMPLES.md`, generated from the exact Pydantic records used by
the evaluator. Examples are synthetic and must not be copied as evidence.

The workspace files are:

| File | Source | Contains | Must not contain |
| --- | --- | --- | --- |
| `manifest.json` | agreed before pilot | interval, target, thresholds | private activity |
| `ground-truth.jsonl` | Emi | short important facts and expected ignores | screenshots, secrets, copied documents |
| `trials.jsonl` | human scoring | counts, scores, truth IDs, condition | full prompts or agent answers |
| `technical-snapshots.jsonl` | measured + reviewed | cumulative quality/invariant counts | memory text or raw paths |
| `resource-samples.jsonl` | measured | CPU, RSS, latency, disk bytes | process arguments or content |
| `privacy-incidents.jsonl` | Emi/reviewer | redacted category/severity/status | captured private payloads |
| `report.md` | evaluator | aggregate metrics and gates | source summaries or answers |

## Minimal ground truth

Record facts close to when they occur, without looking at CONTX output first.
Use one record for each important project/work period, priority change,
decision, blocker, important event, expected ignore, or correction. Mark the
scenarios for which that record is legitimately relevant.

The truth set is intentionally independent. A memory, event, or generated
summary is never promoted into ground truth merely because CONTX produced it.
Expected-ignore entries document noise and privacy boundaries; they do not
increase the important-event recall denominator.

## Paired comparison

For each scenario, prepare at least one stable prompt key:

- `project_resumption`: recent work, decisions, current state, and open
  blockers;
- `recent_understanding`: main projects, time distribution, recurring themes,
  omissions, and noise;
- `change_detection`: resumed projects, increased activity, new repetition,
  and comparison with the previous period.

Run both conditions from the same cutoff and prompt:

1. `without_contx`: a fresh task receives no `contx wake`, `recall`, `zoom`,
   dashboard evidence, or copied CONTX summary;
2. `with_contx`: another fresh task receives the normal active `contx wake`
   contract and may use documented historical inspection only when the prompt
   asks for it.

Do not let one condition see the other answer. Record the same `pair_key`,
`prompt_key`, scenario, and relevant truth identifiers for both. When
practical, hide the condition labels while rating answer quality, then attach
the labels afterward. Partial pairs remain incomplete and do not contribute to
benefit.

## Human scoring rubric

Count a truth identifier as retrieved only when the answer expresses its
material meaning. Wording need not match.

- `supported_factual_claims`: externally checkable claims supported by the
  truth set or direct cited CONTX provenance;
- `materially_false_claims`: claims that would change an action, priority,
  decision, project state, or understanding if believed;
- `irrelevant_claims`: factual details that do not help answer the prompt;
- `duplicate_claims`: repeated claims that add no distinct information;
- `clarification_questions`: questions needed before the answer could be
  useful;
- `relevance_score`: 1 unrelated, 2 mostly noise, 3 mixed, 4 useful, 5 focused;
- `synthesis_score`: 1 incoherent, 2 list without structure, 3 adequate,
  4 clear prioritization, 5 concise and decision-ready.

The score and gates are defined in ADR 0017. False claims are not silently
converted into omissions, and an unsupported claim is not counted as correct
because it sounds plausible.

## Technical and privacy evidence

At least one final technical snapshot must review:

- accepted memories and provenance;
- materially false, irrelevant, and duplicate memories;
- manual corrections;
- sensitive-content and synthetic-secret promotion;
- invalid local-model outputs;
- expired raw records;
- excluded-context captures;
- any outbound user-content transport;
- active context size and wake latency.

Resource samples must cover `idle`, `active_collection`, `model_processing`,
and `web_interaction` across the pilot, not only a favorable instant. The final
report uses nearest-rank p95 for combined measured-process CPU, combined RSS,
and detection latency, plus maximum disk use. `contx pilot sample-resources`
reads only native macOS `libproc` CPU/RSS counters for exact PIDs and safe
directory sizes; it never reads process arguments. The collector PID comes
from the live exclusive lease. Model and web PIDs are explicit to prevent
guessing or broad process scans. A controlled app switch still supplies the
detection-latency measurement; a value must not be inferred from the polling
configuration.

Examples:

```sh
contx pilot sample-resources <directory> --phase idle
contx pilot sample-resources <directory> --phase active_collection \
  --detection-ms <measured-ms>
contx pilot sample-resources <directory> --phase model_processing \
  --model-pid <exact-local-model-pid>
contx pilot sample-resources <directory> --phase web_interaction \
  --web-pid <exact-contx-web-pid>
```

Privacy incidents are recorded immediately with a redacted summary. Do not
copy the offending content into the incident log. A critical unresolved
incident blocks v0 even if behavior scores improve.

## Validation and report

During preparation or the pilot:

```sh
contx pilot validate /absolute/private/pilot-directory
```

For a reproducible cutoff and aggregate report:

```sh
contx pilot report /absolute/private/pilot-directory \
  --at 2026-08-10T08:00:00+02:00
```

The evaluator refuses unsafe permissions, symlinked inputs, oversized files,
duplicate identifiers or condition records, missing truth references,
cross-scenario truth, mismatched pairs, and decreasing cumulative counters.
Evidence after `--at` is ignored.

## Current verification

Focused automated checks prove:

- a complete synthetic three-scenario pilot passes every deterministic gate;
- an unset resource threshold produces `review`, never an implicit pass;
- a premature cutoff and partial pair remain incomplete;
- the 10% false-memory ceiling itself fails because the requirement is
  strictly below 10%;
- mismatched pairs and missing truth references are rejected;
- future evidence is excluded from interim reports;
- workspace and file permissions are private, and resource appends are locked
  and atomically replaced;
- symlinked and broadly readable evidence files are rejected;
- the aggregate report does not contain synthetic ground-truth or prompt keys;
- CLI preparation does not initialize or change the CONTX runtime;
- resource sampling requires a live locked collector, rejects PID double
  counting and symlinked data trees, parses no process arguments, and computes
  CPU from native task-time deltas.

The focused suite currently passes 12 evaluator tests, six resource-probe
tests, and four pilot CLI tests. The native `libproc` probe also returned a
finite CPU/RSS sample for the current process in the target environment. Full
repository totals are recorded only after the complete suite is rerun.
