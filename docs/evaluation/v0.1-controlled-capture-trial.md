# Controlled synthetic capture with the sealed runtime

On 2026-09-12, Emi authorized the next controlled capture step after the manual
Finder/Zen metadata trial. The existing focused-window smoke was executed with
the immutable `1e9e61c48596` release's private Python and installed CONTX module,
using isolated interpreter flags. No source or installed application was changed.
An outer supervisor imposed a 40-second timeout.

The smoke created its own two synthetic AppKit windows. It required the exact
synthetic title before capture, verified rejection after changing the focused
window within that process, and captured the primary window with the production
ScreenCaptureKit source. It requested no permissions and did not initialize or
activate background collection or model processing.

## Observed result

- The smoke exited successfully.
- The focus-race rejection was `focused_window_changed`.
- One 1280 × 856 PNG was written with mode `0600` in a private temporary directory.
- Its SHA-256 was
  `c5b16d383b1a44f8989f64821a0701f62c8b47de2b864adb831acfb476435567`.
- Visual inspection showed the blue synthetic window and its fictitious text,
  without the red secondary window or surrounding application content.
- Normal configuration still had background collection, titles and screenshots
  disabled. The installed application passed strict deep signature verification.

The generated image remains outside Git in temporary storage. Only content-free
results are recorded here.

## Evidence boundary and next gate

This invocation launched the private interpreter directly from the test runner.
It did **not** launch the collector as the installed signed native host's child.
It therefore verifies the sealed runtime's native capture implementation and
the synthetic-window race guard, but does not establish permission attribution
or screenshot persistence through the final application lifecycle.

Before the fifteen-minute trial, run a bounded synthetic capture through that
native host boundary. The current collection policy offers exclusions rather
than an exclusive synthetic-window allowlist; excluding only currently open
applications would not guarantee confinement if another application appears.
Prepare an explicit one-shot synthetic test through the native host, or obtain
agreement on a different precisely bounded method, before enabling live images.
