# v0.4 pattern and candidate validation

**Status:** Complete for the J4 exit gate

**Evidence date:** 2026-08-02

## Outcome

J4 now converts one selected activity-timeline snapshot into conservative
multi-event patterns, fuses related patterns into traceable memory candidates,
and records transparent append-only policy decisions. Every stage has an
explicit source run, version, parameters, output links, and replay result.

The validation used only synthetic semantic events. It did not activate real
collection, inspect screenshots or window titles, contact Ollama, or append a
candidate to OptMem. The deterministic J4 engine aggregates events that were
already defined as local-LLM output; it is not a semantic extraction fallback.

## Implemented boundary

The pattern layer provides:

- project recurrence from at least two distinct events;
- project resumption after a configurable inactivity gap;
- increase, decrease, and new repeated activity across an explicit temporal
  comparison boundary;
- conservative minimum confidence and maximum sensitivity propagation;
- explicit evidence and validity windows with non-mutating expiration;
- deterministic identities, processing-run snapshots, and event foreign keys;
- persisted minimum evidence, gap, ratio, source timeline, and version.

The candidate and worker layers provide:

- case-insensitive per-project deduplication and multi-pattern fusion;
- short autonomous candidate text that does not depend on one fixture name;
- explicit utility, importance, durability, novelty, recurrence, confidence,
  ambiguity, redundancy, sensitivity, score, and scoring version;
- persisted score weights and source pattern run;
- foreign-key-backed candidate-to-pattern evidence;
- append-only accepted, rejected, or deferred decisions;
- stable reason codes for every rejection and deferral;
- persisted source candidate run and all worker thresholds.

## Multi-day proof

The frozen integration fixture contains four semantic timeline events over four
days:

1. one hour on project Atlas in the earlier comparison window;
2. two hours on Atlas after a gap longer than 24 hours;
3. another two hours on Atlas in the recent comparison window;
4. one isolated five-minute event for project Weak.

The initial `temporal-patterns-v1` rules produce exactly three Atlas patterns:

```text
project_recurrence: 3 supporting events
project_resumption: 2 supporting events spanning the inactivity gap
activity_increase: 3 supporting events across the comparison boundary
Weak patterns: 0
```

The three Atlas patterns are fused into one candidate citing all three pattern
identifiers. Through those pattern records, the candidate is backed by the
three distinct source events. The isolated weak event cannot create any
pattern or candidate.

The candidate-text test is parameterized with both `Atlas` and `Orion` and
checks contracts and evidence rather than an exact expected sentence. This
guards against a test passing only because production code contains the name of
one fixture project.

## Replay and threshold proof

Replaying `temporal-patterns-v1` over the same timeline reuses the same three
pattern identities and links them to a second successful run. Replaying the
same candidate scoring version over those patterns reuses the same candidate
identity. Changing the pattern engine to `temporal-patterns-v2` creates three
distinct pattern identities and a distinct downstream candidate while all v1
rows remain queryable.

Two evaluation runs then process the exact same v1 candidate:

```text
acceptance threshold 0.65: accepted, no rejection reason
acceptance threshold 0.95: rejected, below_memory_threshold
```

Both decisions coexist, point to the same candidate, and retain their complete
policy configuration. No candidate state was overwritten to create the
comparison.

## Rejection and deferral proof

Parameterized worker tests exercise every material gate independently:

| Condition | Outcome | Persistable reason |
|---|---|---|
| no multi-event pattern provenance | rejected | `missing_multi_event_pattern_provenance` |
| sensitive candidate | rejected | `sensitivity_not_eligible_for_durable_memory` |
| excessive redundancy | rejected | `redundant_candidate` |
| low-confidence or materially false-looking inference | deferred | `insufficient_confidence` |
| excessive ambiguity | deferred | `ambiguous_candidate` |
| score below the selected threshold | rejected | `below_memory_threshold` |

An accepted decision has no reason. Domain validation requires exactly one
reason for every rejected or deferred decision.

## Persistence and failure boundaries

- A pattern cannot be linked to a processing version different from its own.
- A pattern candidate can cite only patterns selected by its declared source
  run.
- A decision can evaluate only candidates selected by its declared source run.
- Decision policy and threshold must match the persisted evaluation build.
- A candidate scoring build stores the exact weights used by that run.
- The Alembic migration upgrades existing candidates with explicit legacy
  defaults and matches the SQLAlchemy metadata exactly.
- Failed analysis stages use bounded error codes and never persist partial
  successful output sets.

## J4 completion and residual risk

The J4 exit gate is satisfied by synthetic evidence: candidates require
multiple events, retain complete provenance, fuse related patterns, explain all
negative decisions, expire deterministically, and support side-by-side rule and
threshold replay.

The first weights, 24-hour resumption gap, 1.5 change ratio, 30-day validity,
and worker thresholds have not been calibrated on real user activity. Pattern
coverage is intentionally limited to project recurrence, resumption, and simple
time changes. J5 must resolve accepted pattern candidates to event and
observation provenance before writing them to `MemoryStore`; J7 must measure
quality and tune or replace these policies during the explicitly approved real
pilot.
